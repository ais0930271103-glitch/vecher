# Исправление видеозвонков — 0.2.1 (6)

Подготовлено 19.10.2026 для существующего Android-приложения «Вечер» и staging API. При подготовке патча публичный `/app/version` возвращал **0.2.0 (5)**. Наличие этого файла в GitHub означает готовность исходников; публикацию APK и установку на телефоны нужно подтвердить отдельно.

## Причина сбоя

На экране звонка появлялось «Не удалось запустить камеру и звук». Действующий backend сериализует STUN-сервер с `username: null` и `credential: null`. Клиент передавал оба поля без изменений в `flutter_webrtc 1.6.2+hotfix.4`. Android-плагин проверяет наличие ключей, после чего передаёт `null` в конструктор ICE-сервера. Нативный WebRTC отвергает такие значения ещё до запроса камеры и микрофона.

Проверена точная зависимость `io.github.webrtc-sdk:android:150.7871.01`: её [CHANGES.md](https://github.com/webrtc-sdk/android/blob/v150.7871.01/CHANGES.md) указывает исходный commit `73cb8180f7258ee292878d6edd05177f41883962`; в [PeerConnection.java](https://github.com/webrtc-sdk/webrtc/blob/73cb8180f7258ee292878d6edd05177f41883962/sdk/android/api/org/webrtc/PeerConnection.java) явно запрещены `null` username/password.

## Изменения

- Настройки ICE очищаются на границе API и перед вызовом Android-плагина. Отсутствующие поля авторизации STUN опускаются; реальные TURN credentials сохраняются посимвольно. Некорректные настройки получают отдельное сообщение.
- Для восстановления после потери сети используется ожидаемый `restartIce()`, затем создаётся новое предложение соединения. Прежний плоский флаг `iceRestart` Android-плагин не читал.
- Ошибки подготовки соединения, видеоповерхностей, захвата камеры/микрофона и локальных треков различаются. Сырые исключения, SDP и секреты не попадают в сообщения об ошибке.
- Пока исходящий вызов ожидает ответа, Android воспроизводит стандартные гудки. Для входящего на открытом экране звонка используется системная мелодия; учитываются беззвучный режим и выбранная пользователем тишина вместо мелодии.
- Звук останавливается при принятии, отмене, завершении, блокировке приложения, переходе в фон или истечении вызова. Перед запуском WebRTC клиент дожидается остановки проигрывателя и освобождения его аудиофокуса. Повторные запросы сервера не продлевают мелодию бесконечно.
- При возвращении на экран состояние вызова обновляется с сервера перед повторным воспроизведением. Поздняя команда предыдущего экрана не может остановить звук нового вызова.

Звуки ожидания работают в Android-приложении на открытом экране звонка. Фоновый входящий вызов использует существующий FCM-сценарий. Системный полноэкранный входящий вызов Android Telecom и iOS CallKit остаются отдельной задачей.

Начинать проверку нужно с обоими приложениями открытыми: прежнее ограничение запуска камеры в фоне сохраняется. Если вызывающий свернул приложение до ответа партнёра, начало медиа может быть отклонено и звонок завершится. Это отличается от ухода в фон уже начатого разговора, где действует существующий foreground service.

Патч совместим с уже работающим API и TURN. Серверная конфигурация, секреты и порты для этого исправления не меняются.

## Проверка и сборка

Использовать зафиксированные зависимости и Flutter **3.47.7 / Dart 3.13.5**:

```text
flutter pub get --enforce-lockfile
flutter analyze --no-fatal-infos --no-fatal-warnings
flutter test
```

Регрессионные тесты проверяют фактические сообщения Dart → WebRTC MethodChannel, удаление STUN null без изменения TURN, порядок ICE restart, отмену во время подготовки и звуков, а также обновление состояния после возврата из фона. Это проверки кода; прохождение медиа через реальную сеть и качество звука ими не подтверждаются.

Результат локальной проверки 19.10.2026: **69/69 Flutter-тестов**, анализ без ошибок и новых замечаний; сохраняются прежние 2 warnings и 6 infos в других файлах. `CallFeedback.kt`, `MainActivity.kt` и `CallService.kt` вместе скомпилированы Kotlin 2.4 для JVM 17 с официальным Android SDK 36 и точным Flutter embedding. Проверки сертификата, manifest и ABI в Windows-скрипте прошли 17 синтетических примеров под PowerShell 7.6.7; сам скрипт использует синтаксис PowerShell 5.1. Полная сборка и подпись обновляемого APK выполняются на исходном Windows-ПК.

На прежнем Windows-ПК, в существующем репозитории после получения проверенного коммита:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\app\build-staging-update.ps1
```

Скрипт запускает анализ и тесты, собирает обычный arm64 APK с существующим staging API, затем проверяет подпись, application ID, версию и комплект Flutter/WebRTC-библиотек. Ожидаемый сертификат установленного приложения: `bf3d541231287a7e37629088f470d82079d6b1577d0692cceeb8597779d520c1`. Для обновления нужен прежний ключ подписи; создавать или заменять ключ не требуется. Если Gradle использовал другой ключ, проверка останавливает выпуск. Flutter ищется в PATH и в известном каталоге `C:\dev\flutter\bin\flutter.bat`; другой установленный SDK можно указать через `-FlutterPath`.

Итоговые локальные файлы:

- `artifacts/vecher-0.2.1-6.apk`
- `artifacts/vecher-0.2.1-6.version.json`

После `VECHER_APK_READY` для публикации нужны фактические `APK_BYTES` и `APK_FILE_SHA256` этой сборки. Старый сценарий публикации build 5 содержит хеши другой версии; его нельзя применять к build 6 без обновления проверок. Существующий `release.ps1` сразу выполняет сборку и публикацию, поэтому для подготовки проверяемого файла используется новый `build-staging-update.ps1`.

## Проверка на двух телефонах

1. Установить обновление поверх существующего приложения на обоих телефонах; убедиться, что отображается **0.2.1 (6)**, сохранились вход, пара и переписка.
2. Позвонить в обе стороны. До ответа слышны гудки у вызывающего и мелодия у принимающего при разрешённом звуке. После ответа должны появиться двусторонние видео и звук, а мелодии должны прекратиться.
3. Проверить отмену до ответа, отказ, повторный звонок и уход в фон во время ожидания. После отмены звук не должен оставаться; экран завершённого вызова не должен снова зазвонить после возврата.
4. Проверить разговор между Wi-Fi и мобильной сетью, затем переключение сети во время разговора. Отдельно записать слышимость, задержку и зависания видео. Само появление камеры не подтверждает прохождение медиа через TURN.
