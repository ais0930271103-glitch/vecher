# Видео публичных блогов: первый выпуск

Функция по умолчанию выключена (`VECHER_BLOGS_ENABLED=false`). Этот документ
описывает реализованный локально конвейер, а не факт выкладки на сервер.
Обновление схемы `0005_content → 0006_public_blogs` требует отдельного плана
выпуска с согласованным бэкапом и проверенным восстановлением БД. Старый
`deploy-realtime.sh` должен по-прежнему отказывать в такой миграции.

## Граница с личными данными

У загрузки собственные таблица `blog_media_assets`, каталог `blog-media` и
маршруты `/blogs/...`. Она не принимает `ChatAttachment.id`, приватные URL,
произвольные файловые пути или внешние адреса. Исходники чата из `uploads`
зашифрованы и доступны по другим правилам; ни worker, ни его FFmpeg этот каталог
не монтируют. Путь публичного хранилища не может совпасть с `uploads`, лежать
внутри него или содержать его.

Черновик видео виден только текущему владельцу личного блога или текущим
владельцам парного блога. Для остальных авторизованных пользователей нужен
действующий публичный профиль, точные согласия владельцев и опубликованная,
проверенная текущая редакция поста с тем же хешем видео. Отзыв согласия закрывает
последующие запросы видео и обложки. Уже переданные клиенту байты нельзя отозвать;
для новых запросов/диапазонов разрешение проверяется заново.

Worker использует только незашифрованные идентификаторы принадлежности блога,
состояние задания и файлы из своего каталога. Узкие `blog_media_write_lock` и
`require_blog_media_owner` не читают зашифрованные `name`, `bio`, текст черновика,
предпочтения или сообщения. `VECHER_DATA_KEYS`, API JWT, SMTP и Firebase не
передаются worker. Его случайный неиспользуемый JWT существует только для
валидации общей модели настроек; HTTP-сервера и выпуска токенов в worker нет.

## Контракт приложения

| Действие | Запрос | Результат |
|---|---|---|
| Загрузить | `POST /blogs/{blog_id}/media` | `202`, статус задания |
| Проверить обработку | `GET /blogs/media/{id}` | Статус, безопасный код ошибки, готовые адреса |
| Отменить/удалить непривязанное видео | `DELETE /blogs/media/{id}` | `204`; `409 media_in_use`, если видео ещё связано с постом |
| Видео | `GET` или `HEAD /blogs/media/{id}/video` | MP4; одиночный байтовый Range поддержан |
| Обложка | `GET` или `HEAD /blogs/media/{id}/thumbnail` | JPEG; те же правила доступа |

Во всех запросах нужен обычный `Authorization: Bearer ...` с действующим общим
согласием пользователя. URL в DTO относительный, от того же API; токен нельзя
отправлять стороннему видеохостингу. Исходник `.source` не имеет маршрута выдачи.

Загрузка — сырое тело файла, без multipart и Base64. Обязательны точный
`Content-Length`, `Content-Type: video/mp4` или `video/quicktime`, а также
`Idempotency-Key` из 16–64 символов `[A-Za-z0-9_-]`. Приложение создаёт случайный
ключ один раз на выбранный файл и сохраняет его при повторе после потерянного
ответа. Chunked-загрузка без точной длины отклоняется; поток всё равно считается
на сервере, поэтому объявленная длина не позволяет обойти лимит.

Ключ уникален в `(blog_id, uploader_id, client_upload_id)`. Повтор возвращает
существующее задание, не читает тело повторно и не заменяет файл. Другая длина
или MIME с тем же ключом даёт `409 upload_id_conflict`. Ключ обозначает первую
попытку загрузки, а не доказательство равенства байтов: клиентский хеш не
требуется, хеш фактически принятых байтов считает сервер. После `failed`
приложение удаляет непривязанный объект и начинает повтор с новым ключом.
При потерянном ответе оно сначала восстанавливает статус прежним ключом.

Пример статуса:

```json
{
  "id": "UUID",
  "status": "ready",
  "source_bytes": 123456,
  "error_code": null,
  "media": {
    "id": "UUID",
    "status": "ready",
    "url": "/blogs/media/UUID/video",
    "thumbnail_url": "/blogs/media/UUID/thumbnail",
    "duration_seconds": 15,
    "width": 1280,
    "height": 720
  }
}
```

Состояния: `uploading → queued → processing → ready`; ошибки — `failed`, удаление
— `deleting`. `media` до готовности равен `null`. В ошибках и логах нет вывода
FFmpeg, локальных путей или метаданных автора. Основные коды: `invalid_video`,
`unsupported_video`, `video_too_long`, `upload_interrupted`, `upload_timeout`,
`processing_timeout`, `processing_failed`, `source_hash_mismatch`.

`Cache-Control: private, no-store`, `Vary: Authorization` применяются к статусам
и файлам. Видео отвечает `Accept-Ranges: bytes`; полный ответ — `200`, допустимый
одиночный диапазон — `206`, непригодный или многодиапазонный — `416` с размером.
Чтение идёт небольшими порциями из уже открытого безопасного дескриптора.
Новый клиент явно запрашивает `hosted_video=true` у ленты; старый APK такие
материалы не получает.

## Ограничения первого выпуска

| Ограничение по умолчанию | Значение |
|---|---:|
| Исходный файл | 100 MiB |
| Длительность | 180 секунд |
| Нормализованный MP4 | Не более 64 MiB |
| Обложка JPEG | Не более 1 MiB |
| Ожидание загрузки тела | 600 секунд |
| Основной запуск FFmpeg | 300 секунд |
| Один probe/обложка | 20 секунд |
| Lease задания | 900 секунд |
| Повторное получение lease после аварии | Не более 3 попыток |
| Резерв на блог / на весь пилот | 512 MiB / 2 GiB |
| Активные загрузки и задания на блог / всего | 2 / 16 |
| Объекты media на блог / всего | 100 / 500 |
| Свободное место сверх резервов | 256 MiB |
| TTL непривязанных ready/failed/queued и orphan-файлов | 24 часа |

Квота резервируется атомарно **до чтения тела** под теми же блокировками владельца
и блога, что и изменение согласий, плюс глобальная транзакционная advisory lock
PostgreSQL. В резерв входят объявленный исходник, максимально допустимый MP4 и
обложка. Готовый объект занимает фактический размер результата. Неудачная попытка
освобождает байтовый резерв, но её строка и ключ повтора сохраняются до удаления/
TTL и входят в лимит количества: это предотвращает бесконечное накопление строк
ошибок. Свободное место проверяется консервативно с учётом незавершённых резервов.

Вход: один видеотрек и максимум один аудиотрек MP4/MOV; не больше 8.3 млн пикселей
на кадр и примерно 60 fps. Разрешены ограниченные списки декодеров обычных
телефонных форматов. Другие дорожки/неподдерживаемый кодек дают
`unsupported_video`; расширять поддержку надо отдельной проверкой, не включением
всех форматов FFmpeg. Нормализация: H.264/AAC, yuv420p, максимум 1280×720 или
720×1280 по ориентации, без увеличения маленького кадра, 30 fps, MP4 faststart.
Проверяется также длительность и размер фактического результата, наличие звука
и отсутствие неожиданного обрезания по лимиту файла.

## Обработка, сбои и удаление

1. API проверяет владельца и согласие, резервирует квоту и сохраняет `uploading`.
   Запись идёт в отдельный файл с непредсказуемым ключом; байты и SHA-256 считаются
   потоково. `fsync` файла и каталога предшествуют переходу в `queued`.
2. Отдельный worker получает SQL lease с случайным token. Просроченный lease
   позволяет продолжить после аварии. CAS проверяет token перед записью `ready`;
   устаревший процесс не заменит результат нового.
3. Probe и кодирование используют argv без shell, принудительный MOV demuxer,
   `protocol_whitelist=file`, `enable_drefs=0`, `use_absolute_path=0`, ограничение
   потоков, памяти отдельной аллокации, stdout/stderr, процессорного и реального
   времени. Файлы передаются по заранее безопасно открытым FD. Внешние плейлисты,
   сетевые URL и внешние дорожки MOV не загружаются.
4. Глобальные, потоковые метаданные и главы удаляются явно:
   `-map_metadata -1 -map_metadata:s -1 -map_chapters -1`. Остаются технические
   теги созданного контейнера/кодека. Из результата создаётся JPEG; исходник
   никогда не выдаётся. После fsync и проверки результата файлы становятся
   read-only. Только затем готовые ключи/хеш записываются в БД.
5. При потере подтверждения DB commit файлы возможного уже готового результата
   сохраняются. Если CAS доказывает, что commit не состоялся, временные файлы
   удаляются. При успехе исходник удаляется; GC повторяет эту очистку после сбоя.
6. `deleting` сразу закрывает новый доступ. Для используемого постом видео прямое
   удаление запрещено. Освобождение файлов активного обработчика ждёт окончания
   его работы/lease. FK-удаление аккаунта/пары сразу убирает возможность доступа,
   а bounded GC убирает оставшиеся на диске сироты после TTL.

GC работает в media-worker раз в минуту между заданиями, не в 320 MiB API.
Длинное задание может отложить уборку до его завершения. При выключенном worker
периодической очистки нет: оператор должен восстановить worker или явно запустить
режим `python -m app.blog_media_worker --cleanup-only` в том же ограниченном
контейнере. `--once` обрабатывает максимум одно доступное задание. Запуск второго
процесса с тем же каталогом блокируется файловой блокировкой; SQL lease остаётся
защитой на случай старого процесса и перезапуска.

## Контейнер и будущий выпуск

`Dockerfile.media-worker` устанавливает системные `ffmpeg`/`ffprobe`; основной
API Dockerfile их не содержит. Сервис `public-video-worker` находится за profile
`public-video`, имеет отдельные 512 MiB, 1 CPU, максимум 64 процесса/потока,
read-only корневую FS, маленький `/tmp`, `cap_drop: ALL` и `no-new-privileges`.
Его внутренняя Docker-сеть даёт доступ только к БД и не имеет интернет-маршрута.
Worker не получает `env_file: .env`; compose передаёт только DB и перечисленные
настройки обработки. Подпроцесс FFmpeg получает заново собранное минимальное
окружение без DB пароля или любых API секретов. Дополнительный launcher ограничивает
CPU, адресное пространство (1 GiB), размер файла и количество FD, запрещает core
dump. Контейнерный предел resident memory остаётся 512 MiB.

До включения нужны: миграция с проверенным восстановлением `0006_public_blogs`,
отдельный реальный каталог `/opt/vecher-test/blog-media` с uid/gid 10001 и 0700,
проверка свободного диска и бюджета памяти общего сервера, сборка worker image
и реальная обработка тестового MP4 в этой сборке. `prepare-storage.sh` создаёт
каталог; compose не создаёт его молча от root. Caddy продолжает проксировать API;
статического alias к этому каталогу нет. ASGI middleware ограничивает raw upload,
а JSON записей блогов и контента — 32 KiB до Pydantic.

`backup.sh --consistent` теперь останавливает API и только **ранее работавший**
media-worker этого проекта, снимает БД + `uploads` + `downloads` + `blog-media`,
затем возобновляет ранее работавшие сервисы, в том числе при ошибке бэкапа.
Обычный режим остаётся бэкапом одной БД без остановки и не является согласованной
копией видео. Для восстановления нужны совпадающие SQL и файловые части одного
манифеста и отдельно сохранённые ключи API. Этот модуль не изменяет APK, звонки,
TURN, Centrifugo или другие Docker-проекты.

## Проверка

```bash
VECHER_REQUIRE_MEDIA_TOOLS=1 python -m pytest -q tests/test_blog_media.py
```

Тесты используют временную БД и синтетическое маленькое видео, не сервер,
пользовательские ролики или сеть. Покрыты реальная нормализация и метаданные,
закрытый черновик/публичное чтение/отзыв, Range и HEAD, повтор запроса, квота,
неверная длина тела, длительность, обработка без DATA_KEYS, истёкшие lease,
отмена во время обработки, orphan GC, symlink/целостность, timeout/вывод процесса
и потеря подтверждения записи БД. В CI отсутствие FFmpeg/ffprobe — ошибка;
локально соответствующие реальные видео-проверки могут быть пропущены.

Официальные источники параметров: [FFmpeg CLI](https://www.ffmpeg.org/ffmpeg.html),
[протоколы](https://www.ffmpeg.org/ffmpeg-protocols.html),
[MOV demuxer в исходной документации](https://github.com/FFmpeg/FFmpeg/blob/master/doc/demuxers.texi).
Локально проверено на FFmpeg 6.1.1. Версия в фактически собранном Debian image
проверяется отдельно; наличия FFmpeg на рабочей машине для выпуска недостаточно.
