# Публикация готового APK 0.2.1 (6)

Эти два скрипта публикуют конкретную проверенную сборку из коммита
`546df42c42509e4f500013546e9e7d3adf4c6ad6`. Они не запускают Flutter и не меняют APK.
Номер, размер и SHA-256 закреплены в коде; для следующего выпуска нужен новый
проверенный сценарий публикации.

## Входные файлы на Windows

В корне репозитория, в каталоге `artifacts`, должны находиться:

- `vecher-0.2.1-6.apk` — 34299136 байт,
  SHA-256 `73c3f84dd7c16a4d463206957ab9dfa8eb7919237a8ace1ced39b4d1d3f11f75`;
- `vecher-0.2.1-6.version.json` — ровно четыре поля: целое `version_code: 6`,
  строка `version_name: "0.2.1"`, непустые текстовые `notes`, логическое
  `required: false`.

Подпись и манифест этого APK проверены на этапе сборки. Ожидаемый SHA-256
сертификата: `bf3d541231287a7e37629088f470d82079d6b1577d0692cceeb8597779d520c1`.
Публикатор сверяет весь файл APK с проверенным результатом сборки.

Из корня репозитория в Windows PowerShell 5.1:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\infra\staging\publish-apk6.ps1
```

Используется Windows OpenSSH и существующий SSH alias `vecher`. Он должен
разрешаться в `root@94.228.166.214:22`. Настройки перехода через другой SSH-сервер
сохраняются. Скрипт также проверяет UID и имя VPS: `elegant-red` или
`elegant-red.ptr.network`.

## Что происходит на VPS

1. В `/opt/vecher-test/downloads` создаётся отдельный каталог загрузки с правами
   `0700`; в него передаются APK, JSON и Python-публикатор.
2. Публикатор проверяет загрузку, текущую версию 0.2.0 (5), здоровье staging API
   и полный хеш APK, который API отдаёт по HTTP.
3. Текущие APK и JSON сохраняются с манифестом в
   `/root/backups/vecher-test/app-before-0.2.1-6-73c3f84d`. Каталог имеет права
   `0700`, файлы — `0600`. Существующая резервная копия проверяется, а не
   перезаписывается.
4. Подготовленные файлы получают права `0644`. Сначала заменяется `vecher.apk`,
   затем `version.json`. API читает их из общего каталога; перезапуск не нужен.
5. Через `http://127.0.0.1:8092` проверяются здоровье API, метаданные и полный
   хеш отдаваемого нового APK. Итоговый маркер: `VECHER_UPDATE_PUBLISHED_OK`.

Ожидаемый старый APK: 34233600 байт,
SHA-256 `8b2f6157c094fbd4955f90a741836a237c5fcc41caabfeb5502a8f2b0c768124`.
Повторный запуск с уже опубликованным точно таким же APK и JSON проверяет API
и завершается без замены файлов. Другая текущая версия вызывает остановку.

При обрабатываемой ошибке после начала замены скрипт пытается восстановить
старую пару файлов из сохранённой копии. Перед каждой заменой он сверяет
ожидаемое текущее состояние; если оно изменилось, откат останавливается.
Итоговый код при неудачной публикации остаётся ненулевым даже после успешного
отката. Каталог загрузки и резервная копия остаются для диагностики.

Блокировка `.release.lock` согласует экземпляры этого публикатора. Старый
`PUT /app/release` эту блокировку не использует: параллельную публикацию другим
способом запускать нельзя. Две замены файлов не являются общей атомарной
операцией; после принудительного завершения процесса или отключения питания
может потребоваться восстановление из резервной копии.

## Проверки перед передачей пользователю

```bash
python3 -m unittest discover -s infra/staging -p test_publish_apk6.py -v
```

24 теста используют временные файлы и локальный HTTP-сервер. Проверены
публикация, сохранение прав и копии, повторный запуск, ошибки проверки и записи,
откат и защита от замены неожиданного текущего выпуска. Windows helper прошёл
15 сценариев с подставными SSH/SCP и разбор синтаксиса в PowerShell 7.6.7;
нативный Windows PowerShell 5.1 в тестовом окружении недоступен. Скрипт использует
синтаксис 5.1 и избегает проблемного экранирования удалённых команд.

Успех публикации подтверждает раздачу APK локальным API. Затем отдельно
проверяются внешний HTTPS-адрес и звонок между двумя обновлёнными телефонами.
