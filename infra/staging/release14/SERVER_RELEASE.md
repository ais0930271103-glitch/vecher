# Вечер 0.9.0 (14): отдельная процедура сервера

Этот инструмент предназначен только для перехода с проверенного релиза13
(`713b6b3`, API0.8.0, PostgreSQL16, `0005_content`) на исходники
`40e43d85a2e434d4ee2090884a872a507f60fc93`, API0.9.0 и
`0006_public_blogs`. Он не изменяет `check-deploy-schema.py` и не вызывает
обычный `update.sh`: возврат старого API поверх новой схемы не работает.

Инструменты следует загрузить **в отдельный защищённый каталог вне checkout**
и проверить их SHA256 по release-record. Нужны три файла:
`server_release.py`, `media_rehearsal.py` и `diagnose_access.py`.
Последний также проверяется по закреплённому хешу до импорта; импорт
не запускает самостоятельную диагностику или HTTP-запросы.
Рабочий checkout сервера должен
оставаться на точном релизе13 до запуска процедуры.

## Команды

Выполняются от root на утверждённом сервере. Это не инструкция для нового
сервера и не универсальный deployment tool.

```bash
python3 server_release.py preflight
python3 server_release.py deploy
python3 server_release.py enable-blogs
python3 server_release.py status --json
python3 server_release.py public-status --json
```

`preflight` проверяет исходники, реальный код работающего контейнера, API,
схему, PostgreSQL16, точный APK13 и его metadata, конфигурацию и ресурсы.
Он не запускает миграцию и не останавливает сервисы. Требуются свободные
память и диск без расчёта на swap. Сборка и резервные копии получают
дополнительную оценку места по реальным размерам данных и образов.

R3 проверяет один настроенный и один фактический fetch URL нужного
репозитория. Для SSH допустим проверенный псевдоним: штатный OpenSSH должен
разрешить его в `github.com`, пользователя `git` и порт22, без прокси,
динамических команд или отключения проверки ключа. Перед `git fetch`
проверка выполняется снова. Origin и существующие ключи не переписываются;
проверка настройки не заменяет настоящую аутентификацию при fetch.

`public-status --json` выполняет отдельную проверку публичных `/health`
и `/app/version` с VPS, с обычной проверкой TLS и запретом перенаправлений.
Это не loopback-проверка и не доказательство доступности с Windows/Android.
Команда возвращает ограниченный JSON без секретов и при успехе маркер
`RELEASE14_PUBLIC_HTTPS_OK`.

Windows-обёртка по умолчанию проверяет HTTPS с самого Windows до deploy
и после него. Для `Prepare`, `Server` и `Status` разрешён явный параметр
`-HttpsCheck Server`, который использует `public-status` до и после
серверного этапа. Он выводит `SERVER_PUBLIC_HTTPS_VERIFIED` и
`WINDOWS_PUBLIC_HTTPS_NOT_CHECKED`. Для `Build`, `Accept` и `Publish`
этот параметр запрещён. Публикация требует прямой проверки с Windows
до изменения публичных файлов и проверки полного APK после публикации.
`Status` сохраняет полученное по SSH состояние даже при недоступности
HTTPS, явно отмечая частичный результат проверки.

`deploy` выполняет следующие этапы:

1. Берёт существующие `.deploy.lock` и `.backup.lock`, создаёт защищённый
   checkpoint и журнал. Фиксирует исходный контейнер, image IDs,
   фактическое окружение API и неизменённый `.env`.
2. Получает точный Git commit, проверяет tree, собирает API и media-worker
   **до остановки API**, проверяет runtime hashes и сохраняет старые и новые
   образы вместе с текущим образом PostgreSQL. Образы затем выбираются по ID;
   повторной сборки или pull при активации нет.
3. Останавливает только API и при необходимости worker проекта
   `vecher-test`. Сохраняет PostgreSQL dump, `uploads`, `downloads`,
   `blog-media`, `content`, секреты и конфигурацию. API остаётся остановленным
   до окончания репетиции и проверки новой версии.
4. В отдельной internal Docker-сети с новым PostgreSQL16 из **того же image
   ID** восстанавливает точный dump. Проверяет `0005`, отпечатки всех старых
   таблиц, доступность ключей для зашифрованных значений и запуск старого API
   без опубликованных портов и фоновой отправки.
5. На этой копии выполняет `0006`, проверяет неизменность старых таблиц,
   шесть новых пустых таблиц и запуск нового API. Восстанавливает ещё одну
   базу из того же dump. На PostgreSQL проверяет первый `RENAME` с `ROLLBACK`,
   затем атомарную смену двух имён через `BEGIN`/`COMMIT` и принимает старый
   API на `0005`. Рабочее восстановление использует тот же код смены имён.
6. На **другой, новой синтетической базе** проверяет загрузку настоящего
   тестового видео, worker без DATA_KEYS, нормализацию, оба согласия пары,
   модерацию точной версии, чтение третьим пользователем, подписку и отзыв.
   SMTP, Firebase, scheduler, outbox и realtime отключены. Настоящие аккаунты
   и сообщения в этом сценарии не используются.
7. Лишь после этих проверок мигрирует работающую БД. Поднимает временный
   API без портов, с выключенными фоновыми задачами и read-only bind mounts.
   Проверяет API0.9.0, схему, каталог и прежний клиентский контракт.
8. Проверяет или создаёт только internal `vecher-test_media-processing`,
   подключает к ней уже существующий подтверждённый DB-контейнер с alias `db`.
   PostgreSQL не пересоздаётся. Другие сети остаются подключёнными.
9. Записывает в журнал границу возможного открытия трафика, затем заменяет
   только API на проверенный image ID. На этом этапе блоги выключены,
   worker остановлен, APK13 и metadata не изменяются.

`enable-blogs` разрешён только после принятого core deployment и обеих
репетиций. Ещё раз проверяет ресурсный запас и API с включённым флагом во
временном контейнере; запускает worker из зафиксированного образа, проверяет
сеть, отсутствие API-секретов, restart/OOM состояние и доступ к схеме БД
из самого worker через ограниченный по времени read-only запрос; затем включает флаг
только у API. Это необходимый этап **до нативной приёмки APK14**.
Старый APK13 не запрашивает hosted_video, поэтому новые публикации ему не
выдаются. APK публикуется отдельным инструментом после нативной приёмки.

## Восстановление и граница потери данных

До первого открытия трафика процедура при ошибке может вернуть frozen
backup `0005` и **тот же остановленный старый контейнер**. Восстановление
делается в новую БД; новая `0006` сохраняется под отдельным именем, а данные
восстановленной базы проверяются перед переключением. Изменившиеся файлы
или неожиданный schema head останавливают автоматическое восстановление.
Никакого `alembic stamp`, downgrade или удаления новых таблиц нет.
Миграции и `pg_restore` выполняются в именованных контейнерах, зарегистрированных
в защищённом журнале до запуска. Тайм-аут Docker CLI завершает и соответствующий
контейнер; восстановление сначала очищает подтверждённые временные процессы
и ждёт завершения транзакции миграции. Неизвестный временный контейнер
блокирует восстановление до разбора оператором.

После записи `traffic_may_have_opened=true` автоматическое восстановление
старой копии **запрещено**, даже если команда запуска потеряла ответ. Иначе
были бы потеряны новые действия пользователей. Доступный путь отключения
новой функции сохраняет текущую БД:

```bash
python3 server_release.py disable-blogs
```

Он оставляет API0.9.0 и `0006`, выключает блоги и останавливает worker.
Если сам API требует исправления, нужен совместимый с `0006` recovery build.
Восстановление старой копии после открытия трафика — отдельная операция с
осознанной оценкой новых записей, которую данный инструмент не выполняет.

После обрыва процесса незавершённый журнал блокирует новый `deploy`.
Сначала прочитайте `status --json`. Команда `recover` предназначена только
для завершённого backup checkpoint **до** границы открытия трафика.
Переименование обеих баз проходит одной транзакцией; после обрыва проверяются
фактические схема и отпечатки данных. Изменившаяся файловая система,
неожиданная схема или несоответствие сохранённому checkpoint требуют
разбора сохранённого журнала. Старый образ поверх `0006` не запускается.

Checkpoint: `/root/backups/vecher-test/release-14-<32hex>/` (0700).
Указатель — обычный root-owned JSON0600
`/root/backups/vecher-test/release14-current.json`:

```json
{"schema":1,"release":14,"checkpoint":"/root/backups/vecher-test/release-14-<32hex>"}
```

`journal.json` содержит phase, source/runtime/image pins и подтверждения
репетиций. Для APK-публикации допустим только `phase="blogs_ready"` вместе
с независимыми проверками работающих API и worker. `status --json` заново
проверяет работу сервисов; сохранённый `ready` флаг сам по себе не является
доказательством. Значения секретов в stdout не выводятся. Диагностика
неудачных команд остаётся в защищённом `logs/` checkpoint; её нельзя
публиковать целиком. Checkpoint не попадает под14-дневную очистку обычного
`backup.sh` и должен сохраняться отдельно защищённо.

## CI: та же репетиция без сервера и настоящих секретов

CI отдельно собирает старый API из713b6b3, новый API и worker из40e43d8,
получает imageIDs и заранее загружает PostgreSQL16. Затем:

```bash
sudo python3 infra/staging/release14/server_release.py rehearse \
  --workspace "$RUNNER_TEMP/release14-lab" \
  --old-api-image sha256:OLD_IMAGE_ID \
  --api-image sha256:NEW_IMAGE_ID \
  --worker-image sha256:WORKER_IMAGE_ID \
  --postgres-image sha256:POSTGRES_IMAGE_ID \
  --fixture
```

Фиктивная база `0005` и encrypted ContentPreferences создаются старым
образом автоматически. `--backup-dir` можно передать явно; иначе используется
`<workspace>/fixture-backup`. Оба пути должны быть приватными и вне
`/opt/vecher-test`. Никаких mounts рабочих данных, опубликованных портов,
credentials сервера или доступа к production Docker-сетям у этой репетиции
нет. При ошибке разрешена ограниченная диагностика синтетических данных;
production-режим её вstdout не печатает.

## Проверяемые границы

Локальные тесты используют временные файлы и command doubles: блокировки,
подмена checkpoint и архивов, потоковый restore, идемпотентность,
неопределённый результат открытия порта, запрет повторной миграции после
обрыва, очистка временных контейнеров до восстановления, отказ при отсутствии
связи worker с БД, сохранность прежних данных и точное ограничение Docker-команд.
Реальный Docker/FFmpeg/PostgreSQL прогон выполняется отдельной CI-репетицией.
Не заявляйте, что backup production проверен, пока именно его репетиция
не завершилась на сервере.
