ВЕЧЕР — ПОДГОТОВКА ВЫПУСКА 0.9.0 (14), ПАКЕТ R3

СТАТУС: ГОТОВ К ПОДГОТОВКЕ СЕРВЕРА И КАНДИДАТА APK.
Подтверждения тестов, точный commit инструментов и хеши файлов находятся
в release-record.json. В готовом ZIP ready_for_prepare=true. Этот флаг
не означает, что сервер обновлён, APK14 собран или приёмка уже выполнена.
Используйте весь vecher-release-0.9.0-14-r3.zip в новой папке.

R3 принимает SSH-псевдоним репозитория после проверки его фактического
назначения: ровно нужный проект, github.com, пользователь git, порт 22,
штатная проверка ключа сервера. Существующие origin и ключи сохраняются.
Проверка повторяется перед git fetch; смена адреса или небезопасная настройка
останавливает подготовку. Успех диагностики конфигурации не заменяет
настоящую SSH-аутентификацию при получении исходников.

В предоставленной диагностике API и HTTPS работали со стороны сервера,
а Windows получил Timeout ещё до TCP/TLS. Для продолжения через работающий
SSH добавлен явный параметр -HttpsCheck Server. Он проверяет настоящий
публичный HTTPS с VPS и выводит, что доступ с Windows не проверен.
Режим по умолчанию -HttpsCheck Direct проверяет HTTPS с Windows.

1. ПОДГОТОВИТЬ СЕРВЕР И APK

Распакуйте ZIP в новую отдельную папку. Это исключает смешивание R1/R2/R3;
перезапись старой папки через -Force не требуется. Не копируйте один .ps1.
Откройте PowerShell в новой папке и выполните:

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Prepare -HttpsCheck Server

Этот вариант предназначен для подтверждённой ситуации: SSH работает,
а прямой HTTPS с Windows недоступен. Он разрешён только для Prepare,
Server и Status. Build, Accept и Publish не принимают -HttpsCheck Server.

Prepare последовательно:
- проверяет целостность пакета, SSH target и публичный HTTPS с выбранной точки;
- проверяет старый checkout, действующий API/БД/APK и фактический Git origin;
- готовит образы, создаёт согласованную резервную копию и проверяет её
  восстановление, миграцию и откат в изоляции, а также обработку тестового видео;
- обновляет схему 0005_content -> 0006_public_blogs и API до 0.9.0;
- включает проверенный обработчик видео и блоги, проверяет публичный API0.9.0;
- собирает APK14 прежней подписью и сохраняет сведения об исходниках.

В режиме Server выводятся отдельные отметки точки проверки:

  SERVER_PUBLIC_HTTPS_VERIFIED
  WINDOWS_PUBLIC_HTTPS_NOT_CHECKED

Они подтверждают HTTPS с VPS. Они не подтверждают доступ с Windows,
Android или из произвольной внешней сети и не разрешают публикацию APK.
Проверка использует TLS с проверкой сертификата и не следует перенаправлениям.

Если прямой HTTPS с Windows уже работает, можно выполнить Prepare без
параметра -HttpsCheck. Тогда проверка с Windows выполняется до изменения
сервера и повторяется после обновления. Ошибка предварительной проверки
останавливает запуск до deploy.

Bypass действует только в запущенном процессе PowerShell. При других путях
передайте -RepoPath, -FlutterPath и, если необходимо, -AndroidSdk.
Во время создания backup, репетиции и миграции API временно остановлен;
сценарий показывает текущий этап.

Успешные итоговые маркеры подготовки:

  VECHER_APK14_BUILD_READY
  VECHER_RELEASE14_READY_FOR_PHYSICAL_DEVICE_TESTS

Файлы кандидата:
  C:\dev\vecher-update\artifacts\vecher-0.9.0-14.apk
  C:\dev\vecher-update\artifacts\vecher-0.9.0-14.version.json
  C:\dev\vecher-update\artifacts\vecher-0.9.0-14.source.json

Размер и SHA256 APK14 вычисляются после настоящей сборки. Сохраните весь
комплект. APK13 остаётся публичным обновлением до отдельного Publish.

2. ПРОВЕРИТЬ КАНДИДАТ НА ANDROID

Установите APK14 напрямую на тестовые телефоны поверх прежнего приложения
с сохранением данных. Выполните DEVICE_CHECKS.ru.txt: воспроизведение видео,
личный и общий блог, два согласия, проверка оператором, подписка и отзыв.
Проверьте доступ через обычную мобильную сеть хотя бы на одном устройстве.
Существующий APK13 используется для проверки совместимости; удалять данные
ради понижения версии не нужно.

После фактически выполненных проверок:

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Accept

Сценарий проверит сервер и запишет явные ответы о проверках на телефонах
в .phone.json, связанный с конкретными APK, metadata и source SHA.
Отрицательный или отсутствующий ответ не считается успехом.
Успешный маркер: VECHER_APK14_PHONE_ACCEPTED.

3. ОПУБЛИКОВАТЬ ПРОВЕРЕННЫЕ БАЙТЫ

Для этого этапа нужен работающий прямой HTTPS с Windows. Сначала он
проверяется до отправки команды публикации, затем проверяется результат.

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Publish

Publish проверяет сохранённые файлы, приёмку, сервер и подпись, публикует
тот же APK без пересборки. Windows скачивает весь публичный APK по HTTPS,
сравнивает размер и SHA256. -HttpsCheck Server здесь запрещён.

Маркер серверной публикации: VECHER_APK14_RELEASE_OK.
Маркер внешней проверки: VECHER_APK14_PUBLIC_HTTPS_VERIFIED.

Если SSH оборвался или проверка после публикации не завершилась, файлы уже
могли быть опубликованы. Сохраните артефакты и вывод, затем выполните Status.
Повтор Publish использует те же байты и не создаёт новую сборку.

СТАТУС И ОТДЕЛЬНЫЕ ЭТАПЫ

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Status -HttpsCheck Server
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Server -HttpsCheck Server
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Build
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode DisableBlogs

Status возвращает состояние по SSH и отдельно результат HTTPS. Ошибка HTTPS
помечается как частичная проверка; успешные сведения SSH сохраняются в выводе.
phase=no_checkpoint и ready_for_apk14=false означают отсутствие журнала
выпуска14, а не доказательство истории всех операций на сервере.
Server выполняет только серверный этап; Build — только локальную сборку.
DisableBlogs выключает блоги и worker с сохранением текущей БД.

ПОСЛЕ ОШИБКИ

Сначала сохраните вывод и выполните Status. Ошибка WRONG_ORIGIN в предыдущем
запуске возникла до checkpoint, остановки API, backup и миграции; ручное
восстановление БД из-за неё не требуется. R3 заново проверяет текущие факты.

Журнал различает стадии до и после возможного открытия нового API.
До открытия трафика предусмотрено восстановление согласованного checkpoint.
После открытия могли появиться новые записи: старая БД автоматически
не восстанавливается. Не редактируйте журнал и не запускайте старый update.sh
поверх незавершённого перехода. Порядок действий — в SERVER_RELEASE.md.

Сохраните checkpoint после выпуска: в нём находится действующий
runtime-compose.json с закреплёнными образами и флагами. Включать/выключать
блоги следует через этот пакет. Перед будущим обновлением нужна проверка
активной конфигурации: обычный docker compose up с одним базовым YAML
не учитывает сохранённый override.
