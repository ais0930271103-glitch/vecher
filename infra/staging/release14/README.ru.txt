ЕСЛИ ПРЕДЫДУЩИЙ ЗАПУСК ОСТАНОВИЛСЯ НА WRONG_ORIGIN

В прежнем пакете проверка принимала только HTTPS. Это могло отклонить
штатный SSH-адрес того же проекта; сам код ошибки не доказывает формат адреса.
Остановка происходит до создания checkpoint, остановки API и миграции.
Не нужно восстанавливать БД или менять origin ради прохождения проверки.

Распакуйте R2 в новую папку, чтобы не смешивать файлы пакетов. Если папка
уже существует, выберите другую; перезапись через -Force не требуется.
Из новой папки сначала выполните:

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Status

Для ранней остановки без checkpoint ожидается phase=no_checkpoint,
ready_for_apk14=false. Это отсутствие журнала выпуска, а не подтверждение
истории всех действий на сервере. Диагностика показывает checkout_head,
checkout_clean, origin_transport и origin_matches_repository без самого URL.
Публичные версии выводятся отдельно после серверного статуса.

Если origin_matches_repository=true, checkout чистый и HEAD соответствует
выпуску13, можно перейти к Prepare ниже. Он повторит обязательные проверки.
Если origin_matches_repository=false, сохраните вывод Status: потребуются
уточнения фактической настройки, которую сценарий сам не переписывает.

1. ПОДГОТОВИТЬ СЕРВЕР И APK

Распакуйте весь ZIP в отдельную папку; не копируйте один .ps1 отдельно.
Откройте PowerShell в этой папке и выполните:

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Prepare

Bypass применяется только к этому процессу. Настройки компьютера не меняются.
Если пути отличаются, укажите -RepoPath, -FlutterPath и при необходимости
-AndroidSdk с существующими каталогами. Пример:

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Build -RepoPath C:\dev\vecher-update -FlutterPath C:\dev\flutter\bin\flutter.bat

Prepare последовательно:
- проверяет комплект файлов, источник, сервер и исходное состояние выпуска13;
- готовит образы, резервную копию и проверяет восстановление/миграцию отдельно;
- обновляет схему 0005_content -> 0006_public_blogs и API до 0.9.0;
- включает обработчик видео и публичные блоги после серверных проверок;
- собирает и проверяет APK14 прежней подписью, сохраняет сведения об исходниках.

Во время остановки API создание копии, миграция и проверка нового процесса могут
занять время. Вывод сценария показывает текущий шаг. Проект krug, VPN/TURN,
артефакты выпуска13 и подпись не являются объектом этого обновления.

При успешной подготовке в конце:

  VECHER_APK14_BUILD_READY
  VECHER_RELEASE14_READY_FOR_PHYSICAL_DEVICE_TESTS

Файлы:
  C:\dev\vecher-update\artifacts\vecher-0.9.0-14.apk
  C:\dev\vecher-update\artifacts\vecher-0.9.0-14.version.json
  C:\dev\vecher-update\artifacts\vecher-0.9.0-14.source.json

Ни размер, ни SHA256 APK14 заранее не заданы: они вычисляются после настоящей
подписанной сборки. Сохраните весь комплект. Сборка13 остаётся публичным
обновлением приложения до отдельного Publish.

2. ПРОВЕРИТЬ ПРИЛОЖЕНИЕ НА УСТРОЙСТВАХ

Установите полученный APK14 напрямую на тестовые Android-устройства, сохранив
данные приложения обычным обновлением. Выполните DEVICE_CHECKS.ru.txt.
Существующее устройство с APK13 используется для проверки совместимости;
не удаляйте приложение и его данные ради понижения версии.

После фактически выполненных проверок запустите:

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Accept

Сценарий проверит готовность сервера и попросит явно записать результаты
проверок на телефонах. Отрицательный ответ или отсутствие ответа не считается
успехом. Запись .phone.json привязана к конкретному APK, metadata и source SHA.
Accept не публикует обновление. Успешный маркер:

  VECHER_APK14_PHONE_ACCEPTED

3. ОПУБЛИКОВАТЬ ПРОВЕРЕННЫЙ APK

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Publish

Publish не пересобирает приложение. Он повторно проверяет сохранённые файлы,
приёмку, состояние сервера и подпись, затем публикует ровно принятый APK14.
После серверной проверки компьютер скачивает весь публичный APK по HTTPS
и сравнивает размер и SHA256 с локальным кандидатом.

Маркер публикации на сервере:
  VECHER_APK14_RELEASE_OK

Маркер полной внешней проверки:
  VECHER_APK14_PUBLIC_HTTPS_VERIFIED

Если SSH оборвался или внешняя проверка не завершилась, публикация уже могла
состояться. Сохраните файлы и вывод. Сначала выполните Status; повтор Publish
проверяет те же байты и не создаёт новую сборку.

ПРОВЕРКА СОСТОЯНИЯ И ОТДЕЛЬНЫЕ ЭТАПЫ

  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Status
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Server
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode Build
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run-release14.ps1 -Mode DisableBlogs

Status показывает журнал сервера и публичные версии; Server выполняет только
серверный этап; Build собирает только локальный кандидат; DisableBlogs отключает
блоги с сохранением текущей БД. Для каждого запуска используется отдельный
процесс с Bypass, без постоянного изменения политики PowerShell.

При ошибке подготовки серверный журнал различает стадии до и после открытия
доступа к новому API. До открытия можно восстановить согласованный checkpoint.
После открытия пользователи уже могли записать новые данные: старую копию БД
автоматически не восстанавливают. Не меняйте файлы журнала и не запускайте
старый update.sh поверх незавершённого перехода. Сохраните вывод Status для
разбора конкретного состояния. Технические детали — в SERVER_RELEASE.md.

Сохранённый checkpoint содержит также действующий runtime-compose.json с
закреплёнными образами и флагом блогов. Не удаляйте этот каталог после выпуска.
Включение/отключение выполняйте через этот пакет. Перед будущим обновлением
нужно перенести активную конфигурацию: обычный docker compose up только с
базовым YAML не учитывает этот override. Restart/start существующих контейнеров
использует сохранённую конфигурацию самих контейнеров.

СТАТУС ЭТОГО ПАКЕТА

Проверки исходников и инструментов перечислены в release-record.json и PR.
Тестовые команды используют отдельные данные и не означают, что действующий
сервер уже обновлён или APK14 уже собран на Windows. Подпись, реальная сборка,
серверные проверки на целевом хосте и приёмка телефонов выполняются при запуске.
