ВЕЧЕР 0.9.0 (14) — ПАКЕТ ПОДГОТОВКИ R3

ПОДТВЕРЖДЁННАЯ ПРИЧИНА И ИСПРАВЛЕНИЕ

Пользовательская диагностика показала один SSH SCP origin нужного проекта
без подмены fetch URL. SSH alias разрешается в github.com:22, user=git;
проверка ключа сервера не выключена. ProxyCommand, ProxyJump, Match exec,
KnownHostsCommand, LocalCommand и HostKeyAlias в этой Git-настройке отсутствуют.
Это корректная конфигурация, которую прежний буквальный список origin
не поддерживал. R3 проверяет фактическое назначение перед deploy и снова
перед git fetch, сохраняя origin и ключи. Проверка конфигурации сама по себе
не доказывает аутентификацию на GitHub: её выполнит настоящий fetch.

В той же диагностике локальный API и публичный HTTPS со стороны сервера
вернули HTTP200, API0.8.0; metadata APK13 совпала с известными размером и SHA256.
Windows: PowerShell Timeout, curl exit28/HTTP000, DNS выполнен, TCP/TLS
не установлены. Эти данные не определяют причину сетевой недоступности.

R3 добавляет -HttpsCheck Server только для Prepare/Server/Status. Публичные
health/version проверяются с VPS через обычный TLS без перенаправлений.
В выводе явно указано, что Windows HTTPS не проверен. По умолчанию остаётся
Direct с предварительной проверкой до обновления сервера. Publish также
проверяет прямой HTTPS с Windows до публикации и полный APK после неё.
Accept и физическая приёмка не заменяются серверной проверкой.

ГРАНИЦЫ ИСХОДНОГО ОТКАЗА

WRONG_ORIGIN возник после проверки HEAD13 и чистоты checkout, до первого
обращения preflight к Docker. Checkpoint, остановка API, backup, миграция
и сборка APK этим запуском не выполнялись. Могли быть созданы каталог
инструментов и lock-файлы. Последующий Status показал no_checkpoint.

ПОРЯДОК ПРОДОЛЖЕНИЯ

1. Новый vecher-release-0.9.0-14-r3.zip распаковать в отдельную папку.
2. Prepare -HttpsCheck Server: проверить и обновить сервер, создать кандидат
   APK14 на прежнем Windows-PC существующей подписью.
3. DEVICE_CHECKS.ru.txt: физические Android, включая обычную мобильную сеть.
4. Accept: записать реальную приёмку именно собранных байтов.
5. Publish: только при работающем прямом HTTPS с Windows, с полной проверкой
   публичного APK по размеру и SHA256.

ready_for_prepare=true разрешает подготовку, а не подтверждает её результат.
На момент упаковки R3 обновление целевого сервера, signed Windows APK14,
физическая приёмка и публикация APK14 ещё не подтверждены.
Размер и SHA256 APK14 остаются неизвестными до настоящей сборки.
CI использует отдельные данные; backup целевого сервера проверяется только
при его фактической репетиции во время Prepare.

Сохраните checkpoint и runtime-compose.json после обновления. После открытия
нового API старую БД автоматически не восстанавливают; отключение блогов
с сохранением текущих данных описано в SERVER_RELEASE.md.
