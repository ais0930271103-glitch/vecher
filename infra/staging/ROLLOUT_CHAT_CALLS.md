## Что требует устройства, а не только тестов кода

В активном чате уведомление не должно закрывать последнее сообщение, клавиатуру или поле ввода. Новое сообщение в уже открытой переписке не должно дублироваться поверх неё; уведомления из других разделов проверяются с раскрытой и закрытой клавиатурой.

Звонок 1:1 использует WebRTC с целевым видео 720p/30 и адаптацией под сеть. На Android уже начатый звонок поддерживается foreground service с системным уведомлением. При переходе в фон камера выключается, аудио должно продолжиться; начинать захват камеры/микрофона приложение должно из foreground. Входящий звонок при открытом приложении показывается в приложении, в фоне — через FCM-уведомление с переходом по нажатию. **Нативный полноэкранный входящий вызов при убитом процессе и iOS CallKit в этот этап не входят.** Эти ограничения следует объяснять тестировщикам до проверки.

## 1. Подготовить возможность отката

Работать только с `/opt/vecher-test/repo`, Docker-проектом `vecher-test` и, отдельно, `vecher-turn`. Не менять `krug`, его сеть, тома или конфигурацию Caddy.

До обновления сохранить исходный git SHA, копию текущего APK и `version.json`, проверить наличие **действующего `VECHER_DATA_KEYS`** в защищённом хранилище. Для расшифровки старых данных и вложений нужен тот же ключевой набор. Не пересоздавать `.env`, JWT secret, Firebase-ключ, БД или каталоги данных.

Для согласованного бэкапа выбрать время без звонков и загрузок. Если новая версия `backup.sh` ещё не установлена в серверный checkout, использовать проверенную копию этих скриптов, а не объявлять старый DB-only архив полным бэкапом:

```bash
cd /opt/vecher-test/repo/infra/staging
bash prepare-storage.sh
bash backup.sh --consistent
```

`--consistent` останавливает **только `api`**, если он работал, сохраняет БД, uploads и downloads, затем возобновляет API через EXIT trap и при ошибке. База и соседние проекты не останавливаются. Части имеют одну UTC-метку, manifest переносится в итоговый каталог последним. После бэкапа проверить состояние API. Наличие архива и `gzip -t` не заменяет пробного восстановления в отдельном окружении.

Без `--consistent` сохранён старый режим: только БД, без остановки API. Он подходит для прежнего cron, но после появления файлов **не даёт полного восстановления вложений**. Для дальнейших согласованных бэкапов изменить cron в согласованное окно, например:

```cron
15 4 * * * /bin/bash /opt/vecher-test/repo/infra/staging/backup.sh --consistent
```

Это время часового пояса сервера, не обязательно московское. Архивы хранятся 14 дней в `/root/backups/vecher-test`; ключи шифрования хранить отдельно защищённо. Зашифрованные вложения почти не сжимаются: 14 полных копий могут потребовать заметно больше места, чем рабочая квота одной пары. До включения cron проверить запас диска и перенос резервной копии с этого хоста.

## 2. Сначала обновить backend

Проверенный коммит должен быть доступен в серверном checkout. `update.sh` делает `git pull --ff-only`, подготавливает каталоги и пересобирает staging; не использовать его до появления нужного коммита в GitHub. Для отдельного кандидата выбирать его подтверждённый SHA, не произвольное текущее состояние `main`.

На сервере нужны:

- `/opt/vecher-test/downloads` → `/srv/downloads`, прежний канал APK.
- `/opt/vecher-test/uploads` → `/srv/uploads`, владелец **10001:10001**, режим каталога **0700**.
- Существующие `.env` и `secrets/firebase-key.json`; новые значения из `env.example` добавить без замены старых.
- `VECHER_SCHEDULER_ENABLED=true` для очистки незавершённых загрузок и истёкших звонков.

При явном checkout проверенного коммита, после бэкапа:

```bash
cd /opt/vecher-test/repo/infra/staging
bash prepare-storage.sh
docker compose config --quiet
docker compose up -d --build api
docker compose ps
curl --fail --silent --show-error --max-time 5 http://127.0.0.1:8092/health
```

Не использовать `docker compose down -v`. Сначала проверить совместимость **уже установленного APK**: вход, существующую пару и старую переписку. Сверить сохранность данных после изменений схемы на копии существующей PostgreSQL-БД. Успешный `/health` сам по себе не подтверждает корректность миграции, приватности, push, файлов или звонков.

Тесты backend должны пройти до выпуска. Новые маршруты должны отклонять чужую пару и неавторизованного пользователя. Вложения нельзя публиковать через `downloads` или отдельный `file_server` Caddy. Малому API оставлен прежний лимит 320 MiB; параллельные загрузки проверять под этим лимитом.

## 3. Подключить проверенный TURN

Следовать [`../turn/README.md`](../turn/README.md). DNS-имя, публичный IP, сертификат и свободные порты устанавливаются по фактическому хосту. Coturn работает отдельным проектом и не меняет 443/Caddy.

До заполнения `VECHER_TURN_URLS` и `VECHER_TURN_SECRET` функция звонков в staging выключена. После подготовки coturn перенести четыре переменные из его `backend-turn.env` в **существующий** API `.env` и пересоздать только API. Пароли и master secret в APK не вшиваются. Оба сервера должны иметь правильное время; временные credentials рассчитаны на 4 ч 10 мин при максимальном звонке 4 часа.

Перед обычным выпуском нужен проверенный forced-relay звонок, затем возврат обычной ICE-политики. Настройка временного диагностического APK описана в TURN README. **Обычный build должен иметь номер выше и опубликованного APK, и всех диагностических builds, установленных на этих телефонах**, иначе встроенная проверка обновлений может его не предложить.

## 4. Сохранить Android signer и выпустить APK

Обновление установленного приложения требует прежнего application ID и прежнего Android signing key. Текущий проект использует release build, подписанный локальным debug keystore; название `release` не делает новый автоматически сгенерированный ключ совместимым со старым. Не удалять и не регенерировать `.android/debug.keystore` на исходном ПК. GitHub `ANDROID_KEYSTORE_B64`, если применяется, должен содержать **тот же** ключ.

До установки сравнить SHA-256 сертификата текущего APK с кандидатом через Android SDK `apksigner verify --print-certs`. Взятый с другого ПК debug keystore не подходит. Если исходного ключа нет, остановить выпуск и восстановить ключ из существующего ПК/резервной копии; переустановка приложения со сбросом данных не является обычным обновлением.

Номер сборки выбирается после свежего `/app/version` и проверки установленных диагностических APK: он должен строго увеличиваться. По исходной публичной точке следующий номер — как минимум **4**; после диагностической установки build 4 обычному выпуску нужен номер как минимум **5**.

Порядок: получить зависимости → `flutter analyze` → актуальные `flutter test` → release сборка → проверка подписи → установка на два тестовых телефона → проверки ниже. Только после этого опубликовать проверенную сборку штатным способом. `app/release.ps1` не только собирает, но и сразу загружает APK/метаданные на сервер; не запускать его для одной лишь локальной проверки или forced-relay диагностики.

Обычный APK собирается без `CALL_RELAY_ONLY=true`, с прежним тестовым `API_URL`. После публикации сверить `version_code`/описание в `/app/version`, установленный номер на обоих телефонах и отсутствие потери входа/пары/переписки.

## 5. Проверка двух реальных телефонов

| Сценарий | Критерий приёмки |
|---|---|
| Переписка, клавиатура открыта/закрыта | Поле ввода и последние сообщения видны; уведомления не перекрывают чат и не повторяют уже видимое сообщение. |
| Фото, PDF/документ, произвольный разрешённый файл | Отправка, повторное открытие после перезапуска, корректное имя/размер; чужая пара не скачивает файл. |
| Превышение 25 MiB и квоты 250 MiB | Понятный отказ без зависания; API не выходит за память; прерванная загрузка не превращается в видимое сообщение. |
| Оба телефона в одной Wi‑Fi сети | Двусторонние аудио/видео, приём/отказ/отмена, выключение микрофона/камеры, повторный звонок. |
| Wi‑Fi ↔ мобильная сеть | Разговор не менее 10 минут, разборчивая речь и приемлемое видео; записать устройства, операторов и результат. |
| Мобильная сеть ↔ мобильная сеть | Обычный режим, затем отдельная forced-relay диагностика; доказать, что медиа идёт и через TURN. |
| TURN TCP и TURN TLS по отдельности | Соединение и реальная передача медиа с соответствующим единственным URL в тестовой конфигурации. |
| Wi‑Fi → мобильная сеть во время разговора | Обработка потери ICE/повторного соединения; вызывающий клиент выполняет ICE restart. Зависший «идущий звонок» не остаётся бесконечно. |
| Сворачивание и блокировка Android | Камера выключается; аудио продолжается с foreground-service notification; возврат и завершение корректны. |
| Входящий в фоне/после закрытия приложения | FCM-уведомление и переход по нажатию при доступном push; полноэкранный системный incoming UI не ожидается. |
| Разрешение микрофона/камеры отклонено | Понятное объяснение, корректная отмена вызова, возможность повторить после выдачи разрешений. |
| Потеря сети, выключенный второй телефон, занято | Таймаут, завершение состояния и повторный вызов; отсутствие оставшихся включённых камеры/микрофона. |
| Разрыв пары/удаление аккаунта | Доступ к старым приватным файлам/звонку прекращается; физическое удаление подтверждается после commit/плановой очистки. |

Для качества записать фактические условия, прерывания речи и заметные зависания. При наличии диагностических stats — тип выбранного candidate, bitrate, packet loss, RTT и фактическое разрешение; не сохранять SDP, credentials и адреса участников в отчёте. Значение 720p в capture constraints не доказывает, что удалённый телефон получал 720p весь разговор.

## Очистка и восстановление файлов

`scheduler.tick` раз в минуту обслуживает очистку: pending вложения старше заданного TTL (по умолчанию 24 часа), orphan `.bin` без записи БД старше TTL и истёкшие звонки. Просроченные pending дополнительно очищаются перед новой загрузкой пары. Удаление вложений вслед за сообщением/парой/аккаунтом выполняется после успешного commit; rollback сохраняет файл. Метаданные завершённых звонков хранятся до суток, SDP/ICE удаляются при завершении. Отдельного CLI очистки в этом этапе нет.

Не удалять содержимое uploads через `find -mtime -delete`: возраст файла не определяет, нужен ли он сообщению. Если scheduler выключен, автоматическая фоновая очистка не выполняется. Мониторить свободное место в uploads, downloads и backups; квота одной пары не ограничивает сумму всех пар и резервных копий.

Для проверки восстановления поднять отдельный изолированный экземпляр с соответствующим PostgreSQL dump, архивом uploads и **тем же `VECHER_DATA_KEYS`**. Сохранить владельца 10001:10001, проверить старые сообщения и скачивание вложений под двумя тестовыми участниками. Рабочую БД при такой репетиции не перезаписывать. Откат APK — отдельный выпуск с большим build number и тем же signer; просто уменьшенный номер установленный клиент не примет как обновление.
