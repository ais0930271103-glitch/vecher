# Выпуск 0.3.0: синхронизация и очередь уведомлений

Исходная рабочая версия — **0.2.1 (6)**. Она закреплена в `main` коммитом
`5e65d4d69d3a039a902d85edc7f5faf248d2a4f8`; пользователь подтвердил работу звонков.
Этот документ описывает выпуск 0.3.0 из коммита
`40337cc964a74bcffec6aad690c13e8d59ff872d`. Сборка и публикация APK 7, а также
установка на реальный сервер выполняются отдельно от проверки кода.
Следующий пакет бесплатного основного продукта — 0.3.1 (8), см. [PRODUCT_RULES.md](../../PRODUCT_RULES.md).

**Статус:** владелец опубликовал APK 7, обновил телефоны и подтвердил работу.
Ниже сохранена инструкция именно для исходного пакета 0.3.0.
В ветке подготовки 0.4.0 `deploy-realtime.sh` проверяет совпадение текущей и
целевой схемы до остановки API. Переход `0002_outbox` → `0003_evenings`
останавливается с `DEPLOY_SCHEMA_RECOVERY_REQUIRED`: старый API 0.3.x не
запускается с новой версией схемы. Для такого выпуска сначала нужен отдельный
проверенный порядок восстановления. Не применять эту историческую инструкцию
как разрешение на обход новой проверки.

## Что меняется

| Компонент | Поведение |
|---|---|
| API | Сохраняет изменение и намерение отправить уведомление в одной транзакции PostgreSQL. Прежние REST-методы доступны APK 6. |
| Очередь | После commit worker отправляет push или событие Centrifugo; запись переживает остановку API. Повтор ограничен сроком и числом попыток. |
| Centrifugo 6.9.7 | Один процесс, свой пользовательский канал, JWT на 5 минут. Передаются только области экрана для обновления, без текста или идентификаторов личных сущностей. |
| Flutter 0.3.0+7 | Подключается в активном разблокированном приложении; перечитывает данные через REST. После переподключения делает полную сверку. |
| Резервный режим | Пока своего канала нет, сохраняются прежние интервалы опроса 4/10/15 секунд. При подписке остаётся сверка раз в 60 секунд. |
| Alembic | Принятие существующей схемы 0.2.1 и добавление двух таблиц очереди. Staging проверяет миграцию при запуске, не изменяет схему автоматически. |

Push и WebSocket решают разные задачи. Фоновый телефон получает push через FCM;
WebSocket обновляет открытое приложение. Сигнализация звонков и передача медиа
через WebRTC/TURN сохраняют прежний протокол.

## 1. Выбрать проверенный код

Рабочая папка сервера: `/opt/vecher-test/repo`. Используйте полный SHA коммита,
для которого прошли проверки GitHub. `update.sh` больше не выполняет скрытый
`git pull`: он разворачивает именно выбранный checkout.

```bash
cd /opt/vecher-test/repo
git status --short
git fetch origin codex/realtime-durable-events-2026-10-21
# После проверки SHA нужного выпуска:
git switch --detach ПОЛНЫЙ_SHA_ПРОВЕРЕННОГО_КОММИТА
```

Если есть локальные изменения, сохранить и разобрать их до переключения. Не
применять `git reset --hard` к работающему серверу. `.env`, Firebase, DATA_KEYS,
TURN и загруженные файлы находятся вне отслеживаемых файлов.

## 2. Обновить API и включить синхронизацию

Выполнять от root на существующем тестовом сервере:

```bash
cd /opt/vecher-test/repo/infra/staging
bash deploy-realtime.sh --enable-realtime
```

Сценарий последовательно:

1. Проверяет checkout, Compose и Caddy, свободный порт 8093; ставит блокировку
   параллельного обновления. Сохраняет старые образы API/Centrifugo и конфигурацию.
2. Собирает API и проверяет наличие SMTP-настроек без отправки писем. Затем
   делает согласованный бэкап БД, uploads и downloads.
   На время бэкапа и миграции наш API кратко останавливается.
3. Создаёт два разных секрета Centrifugo. Повторный запуск сохраняет их.
   Остальные строки `.env`, включая DATA_KEYS и TURN, не заменяются.
4. Проверяет конфигурацию Centrifugo и выполняет `python -m app.migrate upgrade`.
   При несовместимой старой схеме миграция прекращается до её принятия.
5. Поднимает Centrifugo, проверяет и перезагружает Caddy, запускает API.
6. Проверяет `/health`, номер миграции, настоящий публичный WebSocket,
   запрет чужой подписки/клиентской публикации и получение события от сервера.

Признаки успешного завершения:

```text
MIGRATION_OK=0002_outbox
SCHEMA_HEAD_OK=0002_outbox
REALTIME_WSS_OK
PERSONAL_CHANNEL_ISOLATION_OK
REALTIME_PUBLISH_OK
VECHER_SERVER_UPDATE_OK
```

`DEPLOY_BACKUP=...` указывает каталог возврата. Его не удалять до проверки
двух телефонов. Секретные файлы из него, `.env` и `secrets/centrifugo.json`
не отправлять в чат или GitHub.

В этом выпуске также удалено старое логирование одноразовых кодов входа.
Если сценарий остановился с `SMTP_NOT_CONFIGURED`, прежний API продолжает
работать. Заполнить рабочие SMTP-настройки в серверном `.env`, затем повторить
обновление. Новый сервер не выдаёт коды входа через журнал или HTTP-ответ
staging; `dev_code` существует только в режиме локальной разработки.

Для обновления только API после уже выполненной настройки:

```bash
bash update.sh
```

Этот режим сохраняет текущее значение `VECHER_REALTIME_ENABLED`. Для первого
выпуска с ещё не подготовленным Caddy допустимо обновить только API: новая
очередь заработает, клиент продолжит обычный опрос до включения синхронизации.

### Порты

| Назначение | Адрес |
|---|---|
| Публичный клиент | `wss://api-test.xn--b1aga8b7a.online/connection/websocket` |
| WebSocket на хосте | `127.0.0.1:8093` → Centrifugo 8000 |
| Управляющий API Centrifugo | `http://centrifugo:8001/api`, только сеть Docker |
| REST API | Прежний `127.0.0.1:8092` → API 8000 |

Маршрут Caddy меняется только в `/etc/caddy/vecher-api-test.caddy`.
Главный Caddyfile не переписывается. Админка Centrifugo, история каналов,
presence и публикации из клиентского приложения выключены. Открывать 8093
в UFW не требуется. Порты собственного TURN и krug не меняются.

## 3. Собрать APK 7 на прежнем Windows-компьютере

Этот шаг относится только к скрипту из коммита
`40337cc964a74bcffec6aad690c13e8d59ff872d` в `C:\dev\vecher-update`.
Скрипт в ветке 0.3.1 уже собирает APK 8; его нельзя использовать для подмены APK 7.
Если проверенный APK 7 уже собран, используйте его. Для повторной сборки исходного
пакета 0.3.0 выберите указанный коммит в отдельной чистой рабочей папке и выполните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\dev\vecher-update\app\build-staging-update.ps1
```

Сценарий запускает анализ и тесты, собирает **0.3.0 (7)** для arm64 и проверяет
applicationId, номер версии, необходимые Flutter/WebRTC библиотеки и сертификат.
Ожидаемый сертификат установленного приложения:

```text
bf3d541231287a7e37629088f470d82079d6b1577d0692cceeb8597779d520c1
```

Прежний keystore сохранить. Создание нового ключа сделает обновление поверх
установленной версии невозможным. Результаты находятся в `artifacts/`:
`vecher-0.3.0-7.apk` и `vecher-0.3.0-7.version.json`.

После локальной проверки подписи, package ID, версии и ARM64 зафиксировать размер
и SHA-256 конкретного APK. Опубликовать его через существующий тестовый канал
автообновлений с бэкапом и `required=false`. Затем обновить один телефон поверх
приложения, на втором выбрать «Позже» и проверить APK 7↔APK 6. Обновить второй
телефон и проверить APK 7↔APK 7. Готовность выпуска подтверждается этими проверками;
сама публикация в тестовом канале ещё не является приёмкой.
**`publish-apk6.ps1` предназначен только для прежнего, закреплённого APK 6**;
его нельзя применять к APK 7 или обходить проверку хэша. Новая сборка здесь ещё
не опубликована и удалённо не проверена.

## Проверка на двух телефонах

| Сценарий | Ожидаемый результат |
|---|---|
| Чат открыт на обоих | Сообщение, удаление и статус прочтения отражаются без ожидания обычного опроса. Отправка файлов и звонки работают как в 0.2.1. |
| Экран «Сегодня» | Настроение/радар и доступный ответ обновляются. Ответ партнёра по-прежнему скрыт до собственного. |
| Желания и планы | Видны взаимные совпадения, выбор варианта и запланированный вечер. Личные выборы не раскрываются. |
| Личная заметка/будущее письмо | Собственные устройства обновляются; партнёр не получает уведомления о скрытом действии. |
| Фон, закрытие кодом, выход | WebSocket прекращает работу; закрытый чат не становится прочитанным. Вход в другой аккаунт не возвращает старые данные. |
| Потеря Wi-Fi, переход на мобильную сеть | После восстановления данные сверяются с REST; во время отсутствия канала действует резервный опрос. |
| Перезапуск только API | Уже сохранённое намерение уведомить остаётся в базе и обрабатывается worker после запуска. |
| Разрыв пары | Старые задания удалены; клиент перечитывает состояние. Чужая подписка не становится доступна. |

Проверка FCM в автоматических тестах использует управляемый отправитель.
Фактическую доставку Google, фоновое поведение Android, звук вызова и качество
медиа проверяют на телефонах. Принятие сообщения FCM не означает показ на экране.

## Возврат при неудаче

При ошибке после начала бэкапа сценарий пытается вернуть старые `.env`, образ
API и изменённую конфигурацию Centrifugo/Caddy, затем проверяет старый API.
Сообщение `PREVIOUS_API_HEALTHY` подтверждает эту проверку. Если появляется
`ROLLBACK_INCOMPLETE`, использовать сохранённый каталог для диагностики.

Миграция добавляет таблицы и сохраняет существующие данные; прежний API 0.2.1
может работать с этой схемой. Автоматическое понижение БД не выполняется:
оно потеряло бы новые задания. При возврате старого API очередь остаётся
в базе, но прежний API её не обслуживает. Дальнейший запуск 0.3.0 проверит TTL
и не доставит просроченные задания.
Старый API также не знает новых ключей выполненных заданий: после возврата
возможен повтор напоминания из окна планировщика. Возврат сохраняет данные
и доступность API, но не гарантирует непрерывность доставки уведомлений.

Если миграция пишет `LEGACY_SCHEMA_INCOMPATIBLE`, сохранить точную ошибку.
Не выполнять `alembic stamp head`, не удалять таблицы и не подменять DATA_KEYS.
Сначала сопоставить фактическую схему с сохранённой схемой0.2.1 и сделать
отдельную проверенную миграцию.

## Эксплуатация очереди

В обычных логах нет текста уведомлений, токенов устройств или JWT. Безопасная
сводка состояния через PostgreSQL:

```bash
docker compose exec -T db psql -U vecher -d vecher -c \
  "SELECT kind, state, count(*) FROM delivery_outbox GROUP BY kind, state ORDER BY kind, state;" </dev/null
```

`pending` ожидает отправки, `processing` взят worker под временную аренду,
`delivered` принят провайдером, `cancelled` больше не должен отправляться,
`dead` исчерпал попытки. У завершённых записей удаляется зашифрованное тело,
но сохраняется ключ повтора. Эти записи нельзя чистить вслепую: планировщик
использует ключи, чтобы не отправить старое напоминание заново.

Доставка имеет семантику *at least once*: сбой между подтверждением внешнего
провайдера и записью квитанции может дать повтор. Квитанции по устройствам,
ключи публикации и дедупликация событий в клиенте сокращают это окно. Redis
для одного Centrifugo здесь не требуется: потерянное событие восполняется REST.
Масштабирование Centrifugo на несколько узлов требует общего broker и отдельной
проверки конфигурации.
