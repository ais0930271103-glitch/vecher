# Собственный TURN для звонков «Вечера»

Это опциональный **отдельный Docker-проект `vecher-turn`**. Его профиль `turn` не запускается командами staging API. Здесь подготовлены конфигурация и процедура; работа через реальный NAT и звонки с телефонов ещё требуют проверки.

## Как идут звонки

Backend связывает только участников действующей пары и передаёт сигнальные сообщения WebRTC. Медиа идёт между двумя телефонами напрямую, когда ICE находит рабочий маршрут, либо через coturn. Для мобильных сетей одного STUN недостаточно: прямой маршрут часто недоступен. TURN — транспортный ретранслятор, видеосервер с перекодированием для звонка 1:1 не нужен.

Клиент запрашивает камеру до **1280×720, 30 кадров/с**, ограничивает видеопоток **2,5 Мбит/с** и позволяет WebRTC адаптировать поток. Это целевой режим, а не обещание постоянных 720p при любом интернете. Резервные TCP/TLS-маршруты повышают вероятность соединения, но при потерях могут давать большую задержку. Качество проверяется на двух фактических телефонах.

## Перед настройкой

Нужны фактические значения, которые нельзя заменить произвольным примером:

1. DNS-имя TURN и его публичный IPv4. A-запись должна вести на этот адрес. AAAA пока не публиковать: данный шаблон явно задаёт один IPv4-интерфейс.
2. IPv4 интерфейса TURN-хоста. Если публичный IP назначен самому интерфейсу, local и public равны. Если перед хостом NAT, нужен проброс **того же номера** каждого relay-порта и `external-ip=PUBLIC/LOCAL` (скрипт добавляет его).
3. PEM fullchain и соответствующий приватный ключ от доверенного CA для выбранного DNS-имени. `prepare.py` проверяет цепочку системным хранилищем CA, имя, совпадение ключа и запас срока не менее 7 дней. Самоподписанный leaf отвергается. Скрипт не выпускает сертификаты и не меняет Caddy; используйте существующую автоматизацию сертификатов, например проверку владения DNS у своего CA.
4. Свободные порты и запас ресурсов. Бюджет coturn: 128 MiB RAM / 0,5 CPU, relay range из 41 порта, quota 24 allocations. Это начальные ограничения для проверки одной пары. API по-прежнему ограничен 320 MiB, PostgreSQL — 384 MiB. На общем хосте нужно проверить суммарную память, CPU и трафик, включая другие проекты.

| Входящие порты на TURN-хосте | Назначение |
|---|---|
| 3478 UDP | Основной STUN/TURN |
| 3478 TCP | Резервный клиентский TURN-транспорт |
| 5349 TCP | TURN через TLS с проверяемым сертификатом |
| 49160–49200 UDP | Медиа relay endpoints |

При NAT эти же порты пробрасываются без перенумерации. Firewall также должен допускать исходящие UDP-пакеты от relay к публичным адресам участников и ответный трафик. В шаблоне закрыты private/link-local peer ranges; coturn не должен служить доступом к внутренним сервисам общего хоста.

**Порт 443 на существующем staging принадлежит Caddy.** TURN не проходит через обычный HTTP `reverse_proxy`. Для сетей, которые пропускают только TLS/443, потребуется отдельный публичный IP/хост TURN и отдельная проверенная настройка. Этот шаблон не занимает 80/443 и не изменяет существующие сайты. UDP 5349 не нужен: DTLS-слушатель coturn отключён, UDP-медиа в WebRTC от этого не отключается. `no-tcp-relay` запрещает TCP peer allocations, сохраняя TCP/TLS-клиентские подключения.

## Подготовка на выбранном TURN-хосте

Из каталога `infra/turn`:

```bash
cp env.example .env
chmod 600 .env
sudoedit .env
python3 prepare.py --check-only
sudo python3 prepare.py
```

Заполните в `.env` DNS, оба IP и абсолютные пути к имеющимся сертификату/ключу. `TURN_STATE_DIR` должен быть отдельным пустым каталогом либо ранее подготовленным каталогом этого TURN; путь с посторонними файлами отвергается до смены владельца/прав. При проверке закрытого ключа может понадобиться запуск `sudo python3 prepare.py --check-only`.

Нормальный запуск готовит `/opt/vecher-turn/turnserver.conf`, копии сертификата и ключа в `tls/`, root-only `turn-secret` и `backend-turn.env`. Конфигурация доступна coturn (uid/gid 65534), секрет и backend env — только root. Секрет создаётся один раз и используется повторно при обновлении сертификата. В stdout он не выводится. Файлы из `/opt/vecher-turn` не добавлять в репозиторий и не отправлять в переписку.

Тег `coturn/coturn:4.18.0-r0` проверен по официальному Docker README 18.10.2026. Имена параметров дополнительно сверены с исходным кодом тега `4.18.0`: здесь используются `tlsv1=0`, `tlsv1_1=0`, `dtls=0`, `cli=0`; старые `no-tlsv1` и `no-dtls` из прежних руководств этому релизу не подходят. Тег фиксирует версию, но тег не равнозначен digest. Перед запуском можно получить digest именно из реестра и вписать проверенное `coturn/coturn@sha256:…` в `COTURN_IMAGE`; выдуманного digest в проекте нет:

```bash
docker buildx imagetools inspect coturn/coturn:4.18.0-r0
docker compose --profile turn config --quiet
```

Перед запуском сверить `TURN_LOCAL_IP` с `ip -br address`, DNS с фактическим публичным IP, занятость listener/relay-портов через `ss` и существующие правила firewall. `prepare.py` не открывает firewall, не проверяет DNS по сети и не запускает контейнеры.

После проверки конфигурации и свободных ресурсов:

```bash
docker compose --profile turn up -d coturn
docker compose --profile turn ps
docker compose --profile turn logs --tail=80 coturn
```

Не включайте подробный verbose-лог: для обычной эксплуатации не нужны SDP, временные credentials или IP участников в диагностических отчётах. Ротация Docker-лога ограничена тремя файлами по 5 MiB.

## Связь с backend

Из `/opt/vecher-turn/backend-turn.env` перенесите **значения четырёх одноимённых переменных** в `infra/staging/.env` на API-хосте, сохранив остальные существующие секреты. Файл содержит общий TURN-секрет — передавать его между хостами только защищённым администраторским каналом. Не вставляйте его в `--dart-define`, APK, git или chat.

- `VECHER_STUN_URLS` — JSON-массив со своим STUN.
- `VECHER_TURN_URLS` — JSON-массив из `turn:DOMAIN:3478?transport=udp`, `turn:DOMAIN:3478?transport=tcp`, `turns:DOMAIN:5349?transport=tcp` (порты берутся из настроек).
- `VECHER_TURN_SECRET` — тот же секрет, который находится в `static-auth-secret` coturn.
- `VECHER_TURN_CREDENTIAL_TTL_SECONDS=15000` — 4 ч 10 мин при максимальной длительности звонка 4 часа.

Backend выдаёт участнику активной пары временный username с Unix-временем истечения и HMAC-SHA1 password в Base64. Общий секрет остаётся на серверах. Часы API и TURN должны быть синхронизированы. После изменения TTL/лимита звонка надо сохранить запас времени и повторить проверку длинного разговора/ICE restart.

### Подключение на текущем staging-хосте

Для `/opt/vecher-test/repo`, локального TURN в `/opt/vecher-turn` и домена
`api-test.xn--b1aga8b7a.online` подготовлен `enable-backend.py`. После успешного
запуска coturn и проверки TLS выполнить от root из каталога `infra/turn`:

```bash
python3 enable-backend.py
```

Скрипт проверяет четыре сгенерированных параметра, сохраняет прежний staging
`.env` в `/root/backups/vecher-test/turn-settings/before-turn-<random>.env` с правами
`0600` и атомарно меняет только эти четыре настройки. Остальные строки остаются
без изменений. При дубликатах целевых ключей, многострочных значениях или
неожиданном синтаксисе он останавливается до записи. Домены и порты ограничены
этой конкретной staging-конфигурацией; для другого хоста применим ручной перенос
четырёх настроек, описанный выше.

Затем пересоздать только `vecher-test/api` через `up -d --no-deps --force-recreate
api`. После перехода контейнера в `healthy` выполнить из `infra/turn`:

```bash
python3 enable-backend.py --verify
```

Проверка сопоставляет фактические настройки API с подготовленным файлом,
включая точное равенство общего секрета, и проверяет `/health`. Она выводит только
`API_HEALTH_OK` и `CALLS_ENABLED_OK`. Передачу медиа необходимо проверить отдельно.

До конфигурации TURN `calls/config` показывает `enabled=false`, а создание звонка в staging недоступно. Это позволяет сначала обновить backend, проверить старое приложение, затем включить звонки и выпустить новый APK.

## Обязательная проверка relay

Успешный прямой звонок не подтверждает работу TURN. Для проверки соберите **отдельный диагностический APK**, сохранив прежний Android signing key:

```bash
flutter build apk --release --target-platform android-arm64 --build-name 0.1.0 --build-number 4 --dart-define=API_URL=https://api-test.xn--b1aga8b7a.online --dart-define=CALL_RELAY_ONLY=true
```

Номер `4` допустим только если текущий опубликованный номер всё ещё `3`; перед сборкой проверить `/app/version` и выбрать больший. Установку диагностического APK согласовать на двух тестовых телефонах. **Не выкладывать forced-relay APK через `release.ps1` и `/app/release`.** Для обычного выпуска убрать `CALL_RELAY_ONLY=true`. На debug-сборке клиент может вывести только тип выбранного ICE candidate через `getStats()`, без адресов и credentials.

Если диагностический build 4 установлен поверх текущего приложения, обычному следующему выпуску нужен номер как минимум 5. Учитывайте максимальный номер на обоих телефонах, а не только публичный `/app/version`.

Проверить звонок Wi‑Fi ↔ мобильная сеть и мобильная сеть ↔ мобильная сеть. Для отдельной проверки TCP/TLS временно оставить соответствующий единственный TURN URL в конфигурации тестового API, начать новый звонок с новыми credentials и затем вернуть полный набор. TLS также проверить с другого хоста через `openssl s_client -connect DOMAIN:5349 -servername DOMAIN -verify_return_error -verify_hostname DOMAIN` с **реальным** именем вместо `DOMAIN`. TLS handshake сам по себе ещё не проверяет TURN allocation и передачу медиа.

## Обновление сертификата и обслуживание

После штатного продления сертификата повторить `prepare.py --check-only` и `prepare.py`, затем в окно без звонков пересоздать только coturn: `docker compose --profile turn up -d --force-recreate coturn`. Файлы bind mounts и процесс должны открыть новую пару сертификат/ключ. Автоматическое продление у CA само по себе не обновляет подготовленные копии в `/opt/vecher-turn/tls`.

`max-bps=625000` — **байты/с** на allocation в каждом направлении (5 Мбит/с); `bps-capacity=2500000` — общий начальный лимит в байтах/с (20 Мбит/с). Это ограничения сервера, не обещанная скорость клиента. При нехватке RAM/CPU/канала перенесите отдельный TURN на хост с достаточным запасом; не повышайте ограничения соседних сервисов автоматически.
